# Investigator 0.3.1 — Reasoning-contract repair

Two live `qwen2.5:7b-instruct` runs on v0.3 (INC-002 and INC-004) ended as
`insufficient_evidence` / `incomplete`. In both, the model tagged every finding
`benign_administration`, invented an argument value, and repeated an answered request
until the loop stopped. It never queried host context or network. It was never told
why its claims were rejected.

The verdict gates behaved correctly: no false benign, and unsupported claims were
rejected. The fault was the contract between the application and the model. v0.3.1
repairs that contract. No verdict gate, collection requirement, evidence rule or
security control was loosened.

Specification: [docs/prompts/V0.3.1_REASONING_CONTRACT_REPAIR.md](docs/prompts/V0.3.1_REASONING_CONTRACT_REPAIR.md)
(§11 amended to behavior-based acceptance). Evidence: [docs/validation/v0.3.1/](docs/validation/v0.3.1/).

## What changed

* **Claim definitions (behavior only).** Each available claim has a label, what it
  means, what it does **not** mean, and the evidence it typically needs.
  * `credential_theft` is presented as *LSASS credential-dumping BEHAVIOR*.
  * `account_compromise` is presented as *successful logon after repeated failures
    (POSSIBLE compromise pattern)*.
  * `benign_administration` states that an admin or service account name is not
    evidence of it.

  Intent and outcome are never asserted.
* **Claim and ATT&CK eligibility.** Before the assessment, the model sees:
  * which claims and techniques the retrieved evidence supports, with the evidence IDs
    to cite;
  * which claims and techniques are not supported;
  * which claims are never supported by this build.

  Eligibility is computed with the validator's own predicates. A property test checks,
  on random evidence sets, that "eligible" equals "accepted by validation".
* **Tool argument contract** generated from the Pydantic schemas: allowed values,
  ranges from settings, defaults, prerequisites and one valid example per tool.
  Unknown arguments and values are still rejected.
* **Step feedback** in every decide prompt:
  * `last_step_result`: executed, empty, failed, rejected with the reason, or skipped
    as a duplicate of an earlier call, with the IDs that call returned;
  * `answered_requests`;
  * `collection_checklist`: each benign-closure requirement, with status met,
    not_yet_collected, cannot_be_established or attempted_not_met;
  * `suggested_next_steps` by alert category, excluding requests already answered.
* **Baseline collection.** The application collects host context and, when the trigger
  has a process identity, its process tree before the model's first step. These are
  system-initiated calls through the same dispatcher and the same requirements. A
  failure is a visible failed collection. Setting: `SOCI_BASELINE_COLLECTION`.
* **One validation-feedback revision.** When validation rejects claims, drops
  techniques or findings, or finds invalid references, the model gets one revision.
  It receives only application-generated feedback (rejection reasons, cited IDs,
  eligibility). The revised draft passes through the same gates. The revision cannot
  unlock `benign`. Cancellation during it ends the run as cancelled. Recorded in
  `report.revision`. Setting: `SOCI_VALIDATION_REVISION`.
* **Transparency.** Exports show the model's draft verdict and claims against what
  validation accepted, plus the revision, with the note: "Claims describe observed
  behavior only; intent and outcome are not verified."
* **Evaluation.**
  * `python -m investigator acceptance [--repeats N] [--out DIR]`: behavior-based
    acceptance on the demo fixtures.
  * `benchmark --repeats N`.
  * Per-run diagnostics: claims proposed, accepted and rejected; invalid arguments;
    duplicates; loop stops; revision; prompt tokens.
* **Fixes.**
  * Markdown exports showed `&#x27;` for apostrophes (HTML escaping of quotes).
  * The logon, PowerShell and Defender tools were missing from the coverage
    categories.

### Decision: claim wire values are not renamed

`credential_theft` and `account_compromise` keep their names for compatibility with
stored reports, tests and the API. The behavior-only meaning is carried by the label
and definition shown to the model and in exports. Renaming would change the wire
format without changing the gate.

### Defect found during v0.3.1 validation (present since v0.3.0), fixed

While measuring prompts at `num_ctx 8192`, INC-005 closed as `benign` even though the
trigger's child process and its network connection had been dropped from the
assessment prompt. `model_visibility` said "showed every retrieved record in full".

Cause: at compaction level ≥3, the "shown in full" set was the first 12 ranked records
without being capped at the number actually kept. When fewer than 12 records existed,
omitted records counted as visible.

Fix: `ranked[:min(keep, _SUMMARY_AFTER)]`. This only tightens the gate. Regression
test: `test_D_omitted_tree_records_are_hidden_even_when_fewer_than_the_summary_threshold`;
mutation C11 kills it.

Impact on v0.3.0 with the mock analyst at 8192/2048: two benign benchmark cases
(BM-B01, BM-B05) closed benign with tree records unseen. No non-benign case closed
benign, including under both benign-proposing adversaries
([`visibility_defect_impact.txt`](docs/validation/v0.3.1/visibility_defect_impact.txt)).
At the default 16384 nothing changes.

## Known limitations

* **8192 context with num_predict 2048.** The prompt budget cannot hold the alerted
  process tree for about half of the benchmark cases, which then end `incomplete`
  (honestly, after the fix above). With num_predict 1024, the v0.3.1 contract costs 3
  more cases their full tree view than v0.3 does. Use num_ctx 16384 (the default).
* **Revision is bounded to one round.** A model that ignores it keeps its first draft,
  which is still validated. The revision addresses claim, technique and reference
  losses, not collection gaps.
* **Baseline collection adds 1–2 system calls per investigation.** Tests that assert
  "the model never collected X" run with `baseline_collection=False`.
* **Suggestions are category heuristics.** They never satisfy a requirement by
  themselves; the checklist is the authority.
