# v0.3.1 — Reasoning-Contract Repair (development prompt)

Continue development of Investigator from branch `claude/gracious-dirac-y60p21`
(v0.3.0, commit `ea1d96f`). Implement a narrowly scoped **v0.3.1 Reasoning-Contract
Repair**.

Do NOT loosen any verdict gate, collection requirement, evidence rule or security
control. Do NOT add Windows features, new telemetry sources, new tools, remediation,
cloud models or multi-agent designs. The model still proposes; application code still
decides. The goal is that a small local model (default `qwen2.5:7b-instruct` in Ollama)
can *use* the contract correctly, so that well-collected evidence produces the verdict
it supports.

---

## 1. Evidence: the first live Ollama runs

Two investigations were run by the user with a real local model:
`qwen2.5:7b-instruct`, `--backend fixture`. Their Markdown exports are preserved in
`docs/validation/v0.3/live_ollama_runs/`. If the JSON exports of the same runs are
available, read `trace.llm_exchanges` first to confirm the raw drafts; the Markdown
export does not show the model's original verdict or proposed ATT&CK techniques.

| Run | Alert | Mock model | qwen2.5:7b | Status reason |
| --- | --- | --- | --- | --- |
| `run-f8f901d0…` | INC-004: 8 failed logons + success for `CORP\administrator` from 45.155.205.233 on DC-01 | `likely_malicious` | `insufficient_evidence` (0.30), incomplete | 3 consecutive duplicate requests |
| `run-20201d86…` | INC-002: `rundll32 comsvcs.dll MiniDump` of LSASS to `C:\Users\Public\lsass.dmp` | `likely_malicious` | `insufficient_evidence` (0.30), incomplete | 3 consecutive duplicate requests |

**The evidence the model collected was sufficient.** Replaying each run's exact
collection with correctly chosen claims yields:
* INC-004: `likely_malicious`, `brute_force` + `account_compromise`, T1110 + T1078, no issues.
* INC-002: `likely_malicious`, `credential_theft`, T1003.001, no issues.

Both failures are therefore contract failures, not telemetry or gate failures. The
safety design held: every wrong claim was rejected and no false `benign` occurred. But
two textbook malicious cases produced no usable assessment.

### Failure modes observed

**F1 — Claim misuse (primary).** All 4 findings across both runs were tagged
`benign_administration`, including an LSASS dump and a brute-force success. The prompt
gives `claim_vocabulary` as bare names (`agent.py`: `sorted(attack.CLAIM_RULES)`) with
no meaning or prerequisite. The accounts involved were `CORP\administrator` and
`CORP\svc-backup`, which suggests a lexical association between "administrator" and
"administration". Every finding was then reduced to observations and the verdict to
`insufficient_evidence`.

**F2 — Tool-argument contract.** `tool_catalog()` shows arguments only as
`"any"`/`"string"` (e.g. `get_network_activity.scope: "string"`), with no enum values,
defaults, bounds, required-one-of rules or examples. In run 2 the model invented a
`scope` value and was rejected (`tc-004`). The `get_process_tree` description is stale:
it says "direct children", but v0.2.1 walks all descendants.

**F3 — Duplicate loops.** Both runs repeated one identical request 3 times (INC-004:
`get_logon_activity` ×4; INC-002: `get_process_tree` on the cmd.exe GUID ×4). This
tripped the 3-strike stop and made the run incomplete. The only feedback in the next
state is a `tools_called` entry with `status: duplicate`, which a 7B model evidently does
not act on.

**F4 — Collection planning.** Neither run requested host context or network activity.
The INC-004 run made one real query. The model is never shown what a complete
investigation of this alert type needs, even though the application computes it
(`evaluate_requirements`).

**F5 — No validation feedback.** When validation rejects every claim, the draft is
discarded silently. The model is never told the rejection reasons, which are
deterministic and application-generated.

**F6 — Export defects visible in the logs.**
* `report._markdown_text` runs `html.escape(quote=True)` before backslash-escaping, so
  apostrophes render as `&\#x27;` in the Markdown validation notes.
* `_TOOL_CATEGORIES` has no entries for `get_logon_activity`, `get_powershell_activity`
  or `get_defender_activity`, so the coverage shows "Categories: trigger" after a
  successful logon query.
* The Markdown/HTML do not show the model's original verdict (`verdict_adjusted_from`)
  or its proposed techniques.

## 2. Principle

Make every verdict proportional to the evidence actually collected. This time the fix
is on the input side: give the model a contract it can follow. Keep the application as
the only authority for evidence identity, claim acceptance, ATT&CK acceptance, verdict
gates and benign admissibility.

---

## 3. P0 — Claim contract

1. Replace the bare `claim_vocabulary` in both prompts with application-generated
   definitions, one entry per claim:
   * `claim`
   * `means`: one sentence
   * `does_not_mean`: especially for `benign_administration`, e.g. "an administrator or
     service account was used", "the activity looks routine", "no malicious intent was
     observed"
   * `requires`: the exact prerequisite text from `attack.CLAIM_RULES`
   * `typical_evidence`: categories/indicators

   Generate the entries from one source of truth next to `CLAIM_RULES`, so definitions
   and validator cannot drift. Add the same structure for ATT&CK techniques from
   `attack.CATALOG` (id, name, `requirement`).
2. Add an application-computed `claim_prerequisites_met` section to the final-report
   state. It lists, for the retrieved evidence, which claims' structured prerequisites
   are currently satisfied and by which evidence IDs, using the same predicates the
   validator uses. Also list `claims_not_supported_by_retrieved_evidence`.
   * Label it: "prerequisites met — you decide whether the interpretation applies;
     intent is not verified".
   * `benign_administration` may appear only when its predicate holds.
   * This must not change what validation accepts. Prove it with a test: for random
     evidence sets, the listed set equals the set the validator would accept.
3. Decide whether to rename `benign_administration` (e.g. `managed_agent_execution`) to
   remove the lexical trap. If renamed:
   * keep the old value readable in stored reports (v0.2/v0.3 JSON must still load);
   * map it for validation;
   * update the mock, benchmark truth (`forbidden_claims`) and docs.

   Record the decision and reason.

## 4. P0 — Tool-argument contract

1. `tool_catalog()` must expose, per argument: JSON type, allowed values (enums),
   default, bounds (`ge`/`le`, `max_length`, `pattern`) and a one-line description.
   It must also state required/one-of rules (e.g. "`process_guid` or `evidence_id`")
   and give one valid example call per tool. Build it from the Pydantic schemas so it
   cannot drift.
2. Fix stale descriptions: `get_process_tree` ("ancestry and all descendants").
3. Keep argument validation strict. Rejections already carry precise, application-owned
   messages; make sure the next decide state shows them (see §5).

## 5. P0 — Step feedback and loop contract

1. Add `last_step_result` to every decide state (application-generated):
   * tool, status/outcome, result count, new evidence IDs;
   * for duplicates: `duplicate_of` plus "already answered by tc-00N; its evidence is
     EV-…; choose a different tool or arguments, or finish";
   * for rejections: the validation message and the allowed values.
2. Add `answered_requests`: canonical tool+arguments already executed, with their
   outcome, so the model can see what not to repeat.
3. Keep the 3-consecutive-unproductive stop exactly as it is (it is a safety bound).
   Test that the feedback is present after a single duplicate or rejection.

## 6. P0 — Collection contract

1. Add `collection_checklist` to the decide state: the application's requirement
   evaluation (`process_tree`, `network_activity`, `host_context`, `host_signals`) as
   met / not yet collected / cannot be established, with the reason text. Add
   category-aware *suggested* next steps from the alert type:
   * authentication → logon activity, host context, network;
   * process / process_access → process tree, tree-scoped network, process details,
     PowerShell activity;
   * detection → Defender activity, host context.

   Suggestions are advisory; requirements are unchanged.
2. **Application-owned baseline collection.** Before the model's first step, alongside
   the triggering event, the application itself collects:
   * host context for the alert host;
   * the trigger's process tree when the trigger has a process identity.

   Rules:
   * record them as `initiator="system"`, like the seed;
   * a failure is a visible failed collection, not a silent skip;
   * they count toward requirements exactly as a model call would;
   * they must not satisfy anything a model call could not;
   * document the behaviour change: fixture tool counts will change, so update
     expectations with a note, not silently.

## 7. P0 — One bounded validation-feedback revision

After `validate_report`, if the draft lost claims, techniques or findings to
validation, send the model exactly **one** revision request. It contains only
application-generated text:
* the rejection reasons;
* the per-finding cited evidence IDs;
* `claim_prerequisites_met`.

Validate the revision with the identical gates. Rules:
* The final report is the validated revision. The first draft and its validation stay in
  the audit trace.
* The report states that a revision occurred and what changed.
* No telemetry text is echoed as instruction.
* Never more than one revision.
* Setting `SOCI_VALIDATION_REVISION=false` disables it.
* A benign proposal must still meet every requirement. The adversarial benign proposers
  must still get 0 non-benign closures with revision enabled.

## 9. P1 — Real-model evaluation harness

The deciding evidence for this release is a real model, not the mock.

1. `python -m investigator --llm ollama evaluate` and
   `--llm ollama benchmark [--repeats N]` must record per run:
   * verdict vs truth;
   * proposed / accepted / rejected claims by claim name;
   * invalid-argument rejections;
   * duplicate requests;
   * loop stops;
   * requirement coverage;
   * revision used / changed outcome;
   * prompt tokens (server-reported and estimated);
   * wall time.
2. Add `docs/validation/v0.3.1/ollama_before_after.md`: the two preserved runs as
   "before", and the same alerts plus all 5 fixtures and the 22-case benchmark as
   "after". Use the same model and digest, `temperature=0` and a fixed seed; repeat ≥ 3
   times and report the spread if outputs vary.
3. If Ollama is not available in the development environment, implement the harness,
   run everything else, mark the Ollama results **NOT VERIFIED**, and give the user the
   exact commands to run locally, plus where to save the outputs.
4. Add deterministic regression tests that replay the observed failure behaviour with
   scripted models: `benign_administration` on everything, an invented `scope` value,
   and a triple duplicate. Assert that:
   * the contract now contains the definitions, enums, `last_step_result`, checklist
     and prerequisites;
   * baseline collection happened;
   * the single revision round is offered;
   * a scripted model that follows the feedback on revision ends `likely_malicious`
     for INC-002/INC-004;
   * a scripted model that ignores it stays `insufficient_evidence`.

   Scripted models can prove the mechanics, not that qwen improves; say so.

## 10. Must not regress

* Final gate A–G (v0.2.1) 9/9, including G.
* Benchmark (mock) detection metrics unchanged unless explained.
* Adversarial benign proposers: 0 benign false positives.
* All v0.2.1 (11) and v0.3 (10) mutation checks still killed. Add mutation checks for the
  new guards:
  * the eligibility list equals validator acceptance;
  * the revision count bound is 1;
  * revision cannot bypass benign requirements;
  * baseline failures are visible.
* Prompt budget: the added contract text must fit. Measure with the Qwen2.5 tokenizer
  (`SOCI_TOKENIZER_JSON`) at `num_ctx` 16384 and 8192, and trim or compact definitions
  if needed. No new overflow.
* Windows replay: case G still benign; RW-05 still incomplete.
